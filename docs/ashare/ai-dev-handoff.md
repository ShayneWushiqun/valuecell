# A 股投资助手 AI 开发交接说明

## 1. 文档目的

本文件用于把 `docs/ashare/` 下的阶段文档交给另一个 AI 编码工具执行。目标是让它理解：

- 当前项目要做什么
- 应该先做什么
- 哪些地方不能擅自扩张
- 每一轮开发交付应该达到什么标准

## 2. 重要原则

### 2.1 优先做完整闭环，不优先做大而全

不要一开始同时实现阶段一、阶段二、阶段三。应先完成阶段一最小闭环，再逐步推进。

### 2.2 优先复用现有代码结构

应优先复用仓库里已有的：

- `valuecell.server` 的 API 和 service 模式
- `valuecell.server.db` 的 model/repository 模式
- `valuecell.adapters.assets` 的 A 股数据能力
- `valuecell.core` 的任务和 Agent 编排能力
- `frontend/src/app/home` 的首页与股票相关页面

### 2.3 不要在没有明确需求时自行扩大范围

以下方向在没有明确指令时不要提前实现：

- 自动交易
- 高复杂度 DSL
- 全市场实时高频扫描
- 多市场支持
- 自行接入大量新外部依赖

### 2.4 必须保持可解释

所有输出都应围绕结构化建议卡展开，而不是生成长篇泛泛分析。

## 3. 阅读顺序

1. 先读 [README](./README.md)
2. 再读 [阶段一需求文档](./phase-1-prd.md)
3. 再读 [阶段一技术方案](./phase-1-tech-design.md)
4. 如果阶段一开发完成，再进入阶段二
5. 阶段三只作为中长期目标，不得在阶段一中提前过度设计

## 4. 当前建议的开发目标

如果没有额外说明，默认当前开发目标是：

`仅实现阶段一：持仓与自选中心`

阶段一要形成一个可运行的最小产品闭环：

- 用户可录入持仓
- 用户可管理自选股
- 系统可生成持仓诊断
- 系统可生成每日摘要
- 首页能围绕持仓和自选展示内容

## 5. 对 AI 编码工具的工作要求

### 5.1 每次开发前

需要先输出：

- 它对任务的理解
- 它计划修改哪些文件
- 它打算先实现哪个子目标

### 5.2 每次开发中

需要遵守：

- 尽量小步提交
- 不修改与当前目标无关的模块
- 不重构大范围代码，除非明确有必要
- 尽量在现有命名和目录风格下实现

### 5.3 每次开发后

需要输出：

- 修改了哪些文件
- 完成了哪些目标
- 哪些点仍是暂未实现或待确认
- 跑了哪些测试或校验

## 6. 阶段一的默认交付拆分

建议拆成 4 个连续小目标：

### 6.1 小目标一：持仓数据基础

- 新增持仓模型
- 新增持仓管理能力
- 保证可以增删改查

### 6.2 小目标二：持仓诊断

- 为单只持仓生成结构化建议
- 能持久化诊断结果

### 6.3 小目标三：每日摘要

- 汇总持仓与自选变化
- 输出用户可读摘要

### 6.4 小目标四：前端整合

- 首页显示摘要
- 新增持仓入口或持仓区域
- 可查看最新诊断结果

## 7. 完成定义

如果 AI 编码工具声称“阶段一完成”，至少应满足：

- 后端数据模型和页面不是占位实现
- 用户真的可以录入和查看持仓
- 至少存在一条完整诊断链路
- 至少存在一条完整摘要链路
- 前端可看到系统输出，而不只是日志

## 8. 明确的非目标

当前文档不要求另一个 AI 工具实现以下内容：

- 真正预测收益率
- 证明策略必然赚钱
- 完整事件图谱
- 所有提醒渠道
- 实盘券商连接

## 9. 风险提醒

另一个 AI 工具很可能会犯以下错误，应主动避免：

- 把阶段三内容提前塞到阶段一里
- 一次性新增太多模型和抽象层
- 在没有数据保障的情况下写过度复杂规则
- 为了“看起来完整”而做大量无业务价值的页面

## 10. 推荐交付节奏

建议让另一个 AI 工具按以下方式工作：

1. 先只实现阶段一的数据和后端
2. 再接入阶段一前端
3. 再补测试和文档回写
4. 通过验收后再开始阶段二
