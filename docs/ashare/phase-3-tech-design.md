# 阶段三技术方案

## 1. 目标

建立 ValueCell 的 A 股认知中台，让系统具备基于统一信息链和统一时间轴的多 Agent 裁决能力。

## 2. 设计原则

### 2.1 不做“数据堆砌”

重点不是把更多字段塞给模型，而是把多层数据转成可比较、可对齐、可裁决的上下文。

### 2.2 不做“纯规则爆炸”

面对跨层矛盾信号，避免写成大量 if/else 分支组合。

### 2.3 人可读、机可裁决

所有中间结果既要能被程序消费，也要能被用户理解和复盘。

## 3. 核心架构

阶段三新增一个核心中间层：

`CrossLayer Decision Engine`

它位于数据接入层和最终 Agent 输出之间。

阶段三最重要的技术变化，不是多几个 Agent，而是增加一个稳定的“上下文构建层”，让 Agent 看到的不是碎片数据，而是已经按层级和时间整理过的语义上下文。

### 3.1 新分层

#### 数据接入层

- 行情数据
- 技术数据
- 事件数据
- 资金数据
- 大资金行为数据

#### 语义归一层

将不同来源的数据归一为统一事件对象。

#### 时间轴层

将统一事件按标的和时间排序，形成决策上下文。

#### 裁决层

多 Agent 从不同层审阅上下文，再由总裁决 Agent 汇总。

#### 复盘层

记录建议与结果，支持后续评估。

## 4. 统一事件模型

建议新增统一事件对象 `MarketContextEvent`，字段示意如下：

- `event_id`
- `ticker`
- `layer`
- `event_type`
- `source`
- `occurred_at`
- `ingested_at`
- `importance_score`
- `direction`
- `summary`
- `payload_json`

其中：

- `layer` 对应信息链层级
- `direction` 可标记偏多、偏空、中性、风险、确认等

## 4.1 建模目标

统一事件模型的目的不是存更多字段，而是让不同来源的数据至少满足以下条件：

- 能按时间排序
- 能按标的聚合
- 能按层级区分
- 能进入后续裁决上下文

## 5. 时间轴上下文模型

建议新增 `DecisionContextTimeline`：

- 标的维度聚合
- 时间窗口聚合
- 同层事件聚合
- 跨层冲突标记

输出给 Agent 的不是原始数据流，而是经过预处理的上下文片段。

## 5.1 时间轴层的作用

时间轴层主要解决两个问题：

- 不同层的信息发生顺序不一致
- 用户和模型都难以直接从碎片中看出先后关系

因此阶段三的一个关键设计目标，是把“时间差”变成系统显式可读的内容。

## 6. Agent 拆分

### 6.1 Layer Analyst Agents

建议拆分为：

- `PriceStructureAgent`
- `EventInterpretationAgent`
- `CapitalFlowAgent`
- `BigMoneyRhythmAgent`

### 6.2 Decision Judge Agent

职责：

- 汇总各层观点
- 识别冲突与确认链
- 给出最终动作建议

### 6.3 Review Agent

职责：

- 回看历史结论
- 总结哪些信号组合更有效

## 6.4 阶段三的 Agent 关系

阶段三不推荐把所有能力塞进一个万能 Agent。更适合的模式是：

1. 各层 Agent 负责提出本层观点
2. 总裁决 Agent 负责综合冲突和确认链
3. Review Agent 负责复盘和经验沉淀

## 7. 决策协议

建议所有子 Agent 输出统一协议：

- `thesis`
- `bull_points`
- `bear_points`
- `risk_flags`
- `confidence`
- `timing_view`

总裁决 Agent 再统一生成最终卡片：

- 动作
- 核心假设
- 支持证据
- 反对证据
- 置信度
- 失效条件

## 7.1 为什么需要统一协议

如果没有统一协议，阶段三很容易退化成“每个 Agent 都输出不同风格文本”，最终无法稳定组合。统一协议的意义在于：

- 方便多 Agent 汇总
- 方便前端展示
- 方便后续复盘和评估

## 8. 数据存储设计

建议新增：

- `market_context_event`
- `decision_context_snapshot`
- `decision_record`
- `decision_outcome_review`

## 9. 调度与计算链路

### 9.1 事件入库

所有外部源数据先入统一事件表。

### 9.2 上下文构建

按 ticker 和时间窗口构建时间轴快照。

### 9.3 裁决触发

以下情况触发裁决：

- 阶段二规则层唤醒
- 持仓风险升级
- 用户主动请求分析

### 9.4 结果复盘

在后续时间点记录结果，形成闭环。

## 9.5 建议的实施顺序

阶段三建议按以下顺序推进：

1. 先做统一事件模型
2. 再做时间轴快照
3. 再做 3 层裁决试点
4. 再做复盘闭环
5. 最后扩展更多层级和更多数据源

## 10. 与当前代码的关系

### 10.1 可复用部分

- `valuecell/core/` 中的编排与流式响应能力
- 当前 `watchlist`、`assets`、`tradingagents` 数据通道
- 当前 Agent 执行框架

### 10.2 需要新增部分

- 统一事件模型
- 时间轴快照构建器
- 跨层裁决 Agent 组
- 决策复盘存储与评估

## 11. 实施建议

### 11.1 先做最小闭环

先只选 3 层做试点：

- 行情层
- 事件层
- 资金层

### 11.2 再扩展到 5 层

在试点验证有效后，再逐步引入大资金节奏等更高层数据。

### 11.3 先服务持仓，再服务全市场

阶段三优先服务：

- 用户持仓
- 用户自选

而不是一开始就做全市场全量裁决。

## 11.4 阶段三的测试和验证重点

阶段三不应只测试“代码能跑”，还应关注：

- 统一事件是否正确归类
- 时间轴是否保留了关键先后关系
- 冲突信号是否被正确暴露给总裁决层
- 复盘记录是否可追溯

## 12. 阶段完成标志

当系统能够：

- 将多层信号放在同一时间轴
- 在矛盾信号中给出结构化解释
- 对关键决策进行可回放复盘

即可认为阶段三的核心能力建立完成。

## 13. 给 AI 开发工具的额外说明

如果阶段三由另一个 AI 工具负责实现，必须强调：

- 不要先做复杂页面，先做上下文中台
- 不要一步做成全量信息宇宙，先做最小试点
- 不要为了“智能感”放弃结构化输出
