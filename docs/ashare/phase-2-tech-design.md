# 阶段二技术方案

## 1. 目标

在阶段一的用户资产中心之上，建立“策略定义 -> 规则扫描 -> Agent 裁决 -> 主动提醒”的闭环。

## 2. 总体思路

阶段二采用双层架构：

- `规则层`
  低成本、可持续扫描、负责发现候选和唤醒条件
- `裁决层`
  使用 Agent 对候选标的进行综合分析并输出最终建议

这能避免“大模型全市场轮询”的高成本方案。

阶段二的核心不在于“让模型一直盯市场”，而在于：

- 先用低成本规则筛出少量候选
- 再把高价值候选交给 Agent 处理
- 最终把结论变成用户可执行的提醒

## 3. 领域模型

### 3.1 新增实体

#### `strategy_profile`

字段建议：

- `id`
- `user_id`
- `name`
- `source_type`，值为 `template` 或 `custom`
- `raw_prompt`
- `structured_config_json`
- `status`
- `created_at`
- `updated_at`

#### `strategy_candidate`

字段建议：

- `id`
- `strategy_id`
- `ticker`
- `scan_time`
- `signal_score`
- `trigger_reasons_json`
- `status`

#### `decision_alert`

字段建议：

- `id`
- `user_id`
- `ticker`
- `alert_type`
- `priority`
- `title`
- `body`
- `payload_json`
- `created_at`
- `read_at`

## 3.2 阶段二对象之间的关系

可以按以下逻辑理解：

- `strategy_profile` 代表用户定义的一套监控意图
- `strategy_candidate` 代表某次扫描得到的候选标的
- `decision_alert` 代表最终需要主动触达用户的结果

阶段二的重点是把这三层关系打通，而不是一次性定义所有未来对象。

## 4. 策略表示方式

阶段二不建议一开始做复杂 DSL，而是采用“自然语言 + 结构化配置”的双存储方式。

### 4.1 用户输入

用户可以输入：

- 偏好低估值高分红
- 偏好业绩反转
- 偏好趋势突破
- 偏好回调后再起

### 4.2 系统解析结果

系统将自然语言解析为结构化字段，例如：

- 风格标签
- 观察池范围
- 买入触发条件
- 风险排除条件
- 卖出条件

## 4.3 阶段二的策略抽象建议

为降低实现难度，建议阶段二优先支持以下几类模板：

- 低估值高分红
- 业绩改善或反转
- 趋势突破
- 回调企稳后二次走强

用户的自然语言输入主要用于微调这些模板，而不是完全自由解释所有市场逻辑。

## 5. 扫描引擎

### 5.1 规则扫描职责

规则层负责：

- 扫描自选池和候选池
- 对价格、趋势、基础事件做初筛
- 生成待裁决候选

### 5.2 规则扫描输入

- 用户策略结构化配置
- A 股价格数据
- 历史行情
- 基础新闻/公告摘要
- 基础财务摘要

### 5.3 规则扫描输出

- 候选标的
- 初步触发原因
- 初步优先级

## 5.4 候选生命周期建议

为避免实现歧义，建议阶段二把候选对象理解为一个有生命周期的实体：

- 新发现
- 观察中
- 待裁决
- 已裁决
- 已提醒
- 已失效

这比只生成一次性候选更适合后续提醒和回看。

## 6. Agent 裁决层

### 6.1 新增 Agent

建议新增：

- `StrategyMatchAgent`
- `BuyTimingAgent`
- `SellTimingAgent`

### 6.2 职责拆分

#### StrategyMatchAgent

- 判断候选是否真正符合用户策略本意

#### BuyTimingAgent

- 判断是否进入适合买入或试仓的窗口

#### SellTimingAgent

- 判断持仓是否进入减仓、止盈、止损或破逻辑区间

## 6.3 裁决层输出要求

阶段二的裁决层应优先输出结构化结果，而不是生成长篇自由文本。即使内部使用大模型，也应把结果收敛为：

- 当前动作建议
- 当前判断级别
- 核心理由
- 还缺什么确认
- 失效条件

## 7. 后端模块设计

建议新增：

- `python/valuecell/server/services/strategy_monitor/strategy_profile_service.py`
- `python/valuecell/server/services/strategy_monitor/scanner_service.py`
- `python/valuecell/server/services/strategy_monitor/alert_service.py`

建议新增路由：

- `GET /strategy-monitor/profiles`
- `POST /strategy-monitor/profiles`
- `PATCH /strategy-monitor/profiles/{id}`
- `GET /strategy-monitor/opportunities`
- `GET /strategy-monitor/sell-signals`
- `GET /strategy-monitor/alerts`

阶段二不要求在本文件里补齐所有接口字段，但要求另一个 AI 工具在实现时保证以下能力可被前端消费：

- 用户能管理策略
- 用户能看到候选和提醒
- 用户能看到卖点信号

## 8. 调度设计

### 8.1 扫描频率

初期建议按分钟级或更长周期扫描，不追求毫秒级。

### 8.2 调度拆分

- 周期扫描任务
- 事件触发任务
- 用户主动刷新任务

### 8.3 结果缓存

对候选标的做缓存，避免重复唤醒 Agent。

## 8.4 调度建议

阶段二可优先使用简单定时扫描和页面触发刷新，不要求一开始做复杂事件总线。重点是让结果稳定、成本可控。

## 9. 前端设计

### 9.1 新增策略页

- 策略列表
- 策略详情
- 最近命中记录

### 9.2 新增机会页

- 候选股票卡片
- 买点建议卡
- 观察中状态

### 9.3 新增提醒中心

- 买点提醒
- 风险提醒
- 卖点提醒

## 9.4 前端优先级建议

建议实现顺序：

1. 策略列表和创建入口
2. 机会页
3. 卖点页
4. 提醒中心

如果资源有限，可以先把提醒能力通过页面内列表体现，不必一开始做独立复杂通知系统。

## 10. 成本与性能控制

### 10.1 控制原则

- 规则层先做粗筛
- Agent 只处理高价值候选
- 同一股票短时间内避免重复裁决

### 10.2 限流建议

- 单用户策略数限制
- 单策略候选上限
- 同一股票同一天的重复分析上限

## 10.3 测试建议

阶段二至少应覆盖：

- 策略解析结果的基本测试
- 扫描引擎候选生成测试
- 提醒去重逻辑测试
- 买点和卖点裁决的基本冒烟测试

## 11. 阶段完成标志

阶段二完成的标志是：

- 用户可定义策略
- 系统可持续扫描
- 系统可输出买点和卖点建议
- 系统可以主动提醒，而不是等待用户来问

## 12. 给 AI 开发工具的额外说明

阶段二不要为了“看起来智能”而把全部逻辑交给模型自由发挥。更推荐的做法是：

- 用规则层控制范围
- 用 Agent 做综合判断
- 用结构化对象保存结论
