# 阶段一技术方案

## 1. 目标

在当前代码基础上，最小增量实现一个“以用户持仓和自选股为中心”的 A 股产品形态，并复用现有资产服务、A 股数据接入和 Agent 编排能力。

## 1.1 当前实现回写

本轮已按阶段一最小闭环完成第一版落地，实现与文档的对应关系如下：

- 数据模型已落地：
  - `user_holdings`
  - `holding_diagnoses`
  - `daily_briefings`
- 后端接口已落地：
  - `/api/v1/portfolio/overview`
  - `/api/v1/portfolio/holdings`
  - `/api/v1/portfolio/holdings/{holding_id}`
  - `/api/v1/portfolio/holdings/{holding_id}/diagnosis`
  - `/api/v1/portfolio/briefings/daily`
- 诊断链路已落地：
  - 新增或更新持仓后立即生成首份诊断
  - 支持手动刷新单只持仓诊断
  - 输出结构化建议卡：动作、风险等级、置信度、理由、触发条件、失效条件
- 摘要链路已落地：
  - 首页首次访问时可按需生成最近摘要
  - 支持手动刷新每日摘要
  - 持仓内容优先，自选异动作为补充
- 前端集成已落地：
  - 首页主区域展示每日摘要、持仓列表、持仓诊断
  - 自选股继续复用现有 `watchlist` 侧栏

本轮同时做了以下取舍：

- 暂未单独新增“持仓页”路由，先以首页主区承载阶段一主链路
- 暂未接入固定时间调度，当前优先保证用户触发与首页按需生成链路
- 暂未接入复杂财务裁决或多 Agent 并行推理，先保证结构化、可解释、可运行

## 3. 总体架构

阶段一采用“数据服务 + 轻量诊断 Agent + 产品页整合”的方式实现。

核心思路是：

1. 先建立持仓数据
2. 再把已有 A 股数据能力拼成可用上下文
3. 再生成结构化诊断结果
4. 最后把结果稳定地展示给用户

### 3.1 分层

#### 数据层

- 资产搜索与详情
- A 股价格
- A 股基础新闻
- A 股基础基本面

#### 领域层

- 持仓管理服务
- 自选管理服务
- 持仓诊断服务
- 每日摘要服务

#### Agent 层

- `HoldingDiagnosisAgent`
- `DailyBriefingAgent`

#### 前端层

- 持仓页
- 自选页
- 每日摘要卡片

## 3.2 阶段一开发边界

阶段一的技术设计应尽量克制，避免以下情况：

- 过早抽象出复杂“投资知识图谱”
- 为了后续阶段预留过多未使用对象
- 同时改造过多前端页面
- 引入大量新依赖

阶段一的目标不是“搭好未来三年的全部架构”，而是完成第一个可运行闭环。

## 4.3 字段语义约定

为避免后续实现歧义，阶段一建议遵循以下语义：

- `ticker`：统一使用 A 股标准 ticker
- `quantity`：用户当前持有数量
- `cost_price`：用户持仓平均成本价
- `position_weight`：可选字段，代表该持仓占用户总仓位的大致比例
- `thesis_note`：用户自己写的买入理由或持有逻辑
- `summary`：面向用户展示的简短结论，不是原始模型全文
- `raw_context_json`：用于调试和追溯的上下文快照，不直接给用户展示

## 6. Agent 设计

### 6.1 HoldingDiagnosisAgent

职责：

- 对单只持仓生成结构化判断
- 结合价格、趋势、新闻、基础财务摘要输出建议卡

输入：

- 持仓信息
- 当前价格
- 最近一段历史行情
- 最近公告/新闻摘要
- 基础财务摘要

输出：

- 动作
- 风险等级
- 置信度
- 理由列表
- 触发条件
- 失效条件

补充说明：

- 该 Agent 首期不追求复杂推理链可视化
- 首期重点是稳定输出结构化结果
- 如果新闻、财务或价格数据缺失，应允许退化为较保守的观察结论

### 6.2 DailyBriefingAgent

职责：

- 汇总用户全部持仓和自选的重点变化
- 生成每日摘要

输入：

- 全量持仓诊断结果
- 自选异动摘要

输出：

- 今日重点变化
- 今日建议动作汇总
- 今日重点关注股票列表

补充说明：

- DailyBriefingAgent 的任务不是复述全部数据
- 它应负责压缩信息，告诉用户“今天先看什么”

## 6.3 建议的诊断生成流程

阶段一建议采用固定流水线，而不是复杂自治式 Agent 流程：

1. 读取用户持仓
2. 拉取当前价格和最近行情
3. 拉取最近新闻或公告摘要
4. 拉取可用的财务摘要
5. 组装标准上下文
6. 生成结构化诊断
7. 持久化诊断结果
8. 将最新结果提供给前端

这样的实现更容易被另一个 AI 工具稳定完成。

## 7. 任务调度设计

阶段一不做复杂实时扫描，先做以下两类触发：

### 7.1 用户主动触发

- 新增持仓后立即生成一次诊断
- 用户打开持仓页时按需刷新

### 7.2 定时触发

- 每日固定时间生成一次每日摘要
- 每日固定时间刷新所有持仓诊断

可复用现有任务和对话编排能力，先使用简单定时任务，不强依赖复杂事件驱动。

## 7.3 诊断新鲜度建议

为减少实现歧义，建议系统在阶段一引入“诊断新鲜度”的概念：

- 用户新增或修改持仓后，诊断应视为待刷新
- 每日摘要生成时，应优先使用当天最新诊断
- 如果最新诊断过旧，页面应提示用户刷新，而不是静默使用历史结果

## 10. 风险控制

### 10.1 技术风险

- 新闻和公告质量不稳定，可能导致诊断内容空泛
- 如果一次性诊断所有持仓，调用成本可能偏高

### 10.2 对策

- 先做摘要抽取与上下文裁剪
- 先按持仓数和调用频率做限流
- 首期允许“数据不足时输出观察结论”

## 10.3 技术决策建议

为降低另一个 AI 工具的实现风险，建议明确以下取舍：

- 首期允许同步/异步混合实现，但 I/O 密集路径优先使用异步边界
- 首期不要求多 Agent 并行复杂编排
- 首期不要求对所有诊断结果做长期历史分析
- 首期允许页面用列表卡片展示，不要求复杂可视化

## 10.4 测试建议

阶段一至少应覆盖以下测试类型：

- 持仓模型与 repository 基础测试
- 诊断服务单元测试
- 摘要服务单元测试
- 关键 API 冒烟测试
- 首页和持仓页的基本渲染验证

## 11. 阶段完成标志

当以下条件满足时，可认为阶段一完成：

- 用户可以维护持仓和自选
- 系统可生成结构化持仓建议
- 系统可生成每日摘要
- 首页已从“通用聊天入口”升级为“资产状态入口”

## 12. 给 AI 开发工具的额外说明

阶段一文档的重点是帮助另一个 AI 工具做出“能运行的产品能力”，而不是做出“理论上最完整的投资框架”。如果在实现过程中发生冲突，应优先保证：

- 能录入数据
- 能产出建议
- 能展示结果
- 能基本测试
